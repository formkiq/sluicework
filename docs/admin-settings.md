# Central administration and guided setup

Use one main Sluicework admin for the whole cluster. Workers connect outbound;
they have no separate admin console, admin password, or GitHub App private key.
Normal setup and resource changes use forms, not hand-edited JSON. Installation
identity and private keys remain protected files generated by setup.

## Enable access over WiFi

1. On the server Mac, sign in and open **Settings → Network access**.
2. Enable HTTPS, enter a stable local hostname and choose a free port (default
   `8443`). On macOS, obtain the local hostname from **System Settings → General
   → Sharing**, or `scutil --get LocalHostName`, and append `.local`.
3. Save. Sluicework validates the port, creates a cluster CA and a server
   certificate for that hostname, and starts an additional HTTPS listener. The
   existing primary connection and local workers remain available. Allow the app's
   incoming connections in the host firewall when required; WiFi clients must be
   able to communicate with one another. Router port forwarding is unnecessary.
4. Download the **public CA** and compare its SHA-256 fingerprint with the main
   admin before trusting it on another machine. For browser access on a Mac,
   import it in Keychain Access and configure SSL trust. Worker setup uses its
   own verified CA file and does not alter system trust.

The admin displays the HTTPS URL, certificate expiry, public CA and fingerprint.
Leaf certificates renew automatically while retaining the CA. To replace lost or
expiring root trust, explicitly select **Replace the cluster CA** and distribute
and verify the new public CA on every connected worker. A hostname change also
requires updating worker connection setup. Changing the port reserves the new
listener first; an occupied port leaves the previous configuration intact.
Disabling network access disconnects workers using that endpoint, while the
primary listener stays available.

## Configure the GitHub App

In **Settings → GitHub App connection**, enter the App ID, installation ID and
`owner/repository`, then upload the PEM RSA private key. Install the App only on
the intended repositories and grant **Administration: read/write**, **Metadata:
read** and **Actions: read**. No OAuth callback or webhook is required for this
server-to-server integration.

Save, then **Test saved connection** to verify runner access and Actions read
using separate scoped tokens. Existing keys are masked and never returned. A
replacement key for the same connection preserves registrations. Before changing
App IDs, installation or repository, drain runners and wait for their registrations
to clear. A missing key after restore is reported in Settings so it can be uploaded
again without preventing access to the main admin.

## Join another Mac or Linux machine

For an existing external GitHub runner, use **Actions runners** instead of
enrolling it as a Sluicework worker. [GitHub Actions administration](github-actions-admin.md)
covers organization runners, labels, registration/removal and published placement.

1. Open **Machines → Enroll machine** in the main admin. Enter its name, choose
   **Optional CI workstation** or **Script and AI worker**, select its actual OS
   and architecture, and use the configured HTTPS cluster URL.
2. Prepare setup, then download the worker ZIP. It contains the helper, generated
   bootstrap, checksums, instructions, public CA when applicable, and a binary
   only when the requested platform matches the server. For another platform,
   obtain its binary from the matching installer/platform build and place it in
   the extracted folder. Enrollment tokens and private keys are not bundled.
3. Extract into a new directory owned by the worker's normal non-root login.
   Verify `SHA256SUMS`. CI workstations need rustup, Python 3.12 and, on macOS,
   Xcode Command Line Tools; script/AI workers need Python 3.9+ for the helper.
4. In that directory run `chmod 700 ./sluicework ./manage`, then
   `python3 ./manage join`. Compare any bundled CA fingerprint with the main admin
   and paste its one-use token at the hidden prompt. The helper generates local
   paths and credentials; it does not ask for a worker admin account.
5. Return to **Machines**. For CI, approve the GitHub runner and choose its
   resource settings, then **Offer capacity**. For script/AI workers, set labels,
   slots and approved jobs. Use trusted workloads under personal logins; these
   processes use that OS account's permissions.

`manage start`, `status`, `pause` and `stop` on a remote worker affect that worker
only. Stopping a script/AI worker drains its active work before exit; clear its
machine drain in the main admin to resume claims. A workstation starts paused
after a restart, and the main admin must make a fresh capacity offer.

## Change operating settings

In **Machines → GitHub runner → Configure**, manage build threads (1–8), CPU load,
free memory, idle time, AC power and availability-window length. Machine cards
show requested and reported settings, with pending changes while a build finishes
or a worker is offline. No server/controller restart is needed to apply a profile.
Settings are editable as soon as Configure opens. To return to the machine's
local defaults, choose **Restore installation defaults**, then save.

**Offer capacity** creates a bounded, explicit request. **Pause capacity** stops
new work while assigned builds finish. A newer local pause wins over an earlier
admin offer, and old offers never enable a restarted controller. The existing
machine **Drain** remains a separate cluster-wide admission gate.

**Settings → Retained output** controls the per-attempt retention cap without a
server restart. Settings and requests are administrator-only, persisted in SQLite
and audited. Browser sign-in to the same main admin works over its HTTPS URL.

## Bootstrap and recovery

The initial storage directory/listener and host identity are installation inputs,
visible under **Settings → Installation details**. Moving storage uses backup and
restore rather than changing a path underneath the running database. Connection
trust and enrollment are generated by the guided join flow. Internal credential,
runner-JIT and status files are not editable configuration.

Database backups include managed settings, runner profiles and requests. Escrow
`<dataDir>/configuration-secrets/` separately in encrypted storage: it holds the
managed CA signing key, TLS key and uploaded App keys, and is deliberately absent
from downloadable worker bundles and API responses. Preserve the original bootstrap
files as well. See [recovery](recovery.md) before restoring or changing trust.
